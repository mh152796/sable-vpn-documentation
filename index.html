Sable Documentation

Welcome to the documentation for Sable, a self-hosted VPN platform made of three projects: a Flutter VPN app for Android and iOS, a NestJS backend API with an agent for your VPN servers, and a Next.js admin panel. Follow this guide to set everything up, brand it and publish it.

What is in this package:
  • sable-vpn/ — the Flutter app (Android and iOS, including the iOS tunnel extension).
  • sable-backend/ — the NestJS + PostgreSQL API, plus the VPN node agent in sable-backend/node-agent/.
  • sable-admin/ — the Next.js admin panel.
  • Documentation/ — this guide.
Setting up for the first time? Start with the backend (section 13), then the admin panel (section 14), then add your first VPN server (section 15), then come back to section 1 for the app. The app and the admin panel both need a running backend, and the app needs at least one active VPN server to connect to.

Feature Walkthrough

A plain-language tour of what the app does, so you can find your way around before touching any code. Nothing in this section needs programming knowledge — the technical setup starts at section 1.

First launch and sign-in

  • Sign in — email and password, or Google. New users create an account with their email; the backend emails a one-time code to confirm it. A forgotten password is reset the same way.
  • Device limit — each plan allows a number of devices at once (1 on Free, 5 on Premium by default). When the limit is reached, the user is asked to sign out another device first.
  • Maintenance and updates — if you turn on maintenance mode or require a newer app version in the admin panel, users see that message at launch.

Connecting

  • One-tap connect — the Home screen has a large connect button. Once connected it shows the connection time, upload and download speed and the data used.
  • Locations — users search locations, see recent and favourite servers and each server's current load. Each location is Free, Ads (unlocked by watching an ad) or Premium.
  • Protocol — WireGuard, V2Ray (VMess over TLS) or Auto, which lets the app choose.
  • Light and dark theme — the whole app follows the system setting or the user's choice.

Free time, rewarded ads and Premium

  • Daily free time — Free users get a daily allowance of VPN time (60 minutes a day by default).
  • Rewarded ads — users watch a short ad to add time or to unlock an Ads location. Each step on the reward ladder adds more minutes. The backend adds the time only after AdMob confirms the ad was watched.
  • Premium — monthly or yearly subscriptions through Google Play and the App Store (via RevenueCat): all locations, no ads, more devices and no time limit. Users can restore purchases.
  • Promo codes — codes you create in the admin panel give a plan for a set time.

Tools

  • Speed test — measures latency, jitter, download and upload speed through the tunnel.
  • Split tunneling — on Android, users choose apps that skip the VPN. On iOS, they choose domains, because iOS does not allow per-app splitting.
  • Kill switch — on iOS, a setting in the app blocks traffic when the VPN drops. On Android, the app guides users to the system's Always-on VPN setting.

Account and settings

Current plan, change password, signed-in devices (sign any of them out), theme, language (English, Bangla, Arabic, Russian and Ukrainian), support messages, debug logs, legal pages, sign out and delete account.

What you control from the admin panel

Almost everything users see is managed in the browser, without rebuilding the app: VPN servers and regions, plans and store products, promo codes, rewarded-ad rules, announcements, push notifications, minimum app version and maintenance mode, the privacy policy, terms and about pages, app users, support messages and integration keys. The full list is in section 14.

Recommended first hour. Set up the backend (section 13), start the admin panel (section 14) and sign in. Add a region and one VPN server with the install command (section 15) and activate it. Then point the app at your backend (section 8) and run it on a real phone — create an account, tap Connect and check that your IP address changes. Once that round trip works, move on to branding, Firebase and store setup.

How the Pieces Connect (Architecture)

Sable is three projects plus one small agent on every VPN server. Only the backend talks to the database and holds secrets. The app never sees another user's data, and the admin panel never talks to PostgreSQL directly.

ConnectionWhat happens
App → BackendEvery request goes to https://api.your-domain.com/api/v1/... with the user's Sable access token in Authorization: Bearer and device headers (X-Device-Id, X-Platform, X-App-Version). Access tokens last 15 minutes and are renewed with a refresh token.
App → Firebase → BackendFor Google sign-in, Firebase returns an ID token. The app sends it to POST /auth/social; the backend checks it with the Firebase Admin SDK and returns Sable tokens. Email sign-in does not use Firebase.
App → Backend → VPN serverWhen the user taps Connect, the backend picks a server, creates a WireGuard peer or a V2Ray user for that session and returns the tunnel settings. The app then connects straight to the VPN server. VPN traffic never passes through the backend.
VPN server (node agent) → BackendThe agent on each server sends health and load every 30 seconds and applies new or removed peers every 5 seconds. It signs in with the agent token from the install command.
Admin panel → BackendThe admin signs in with the email and password set in the backend .env. The panel keeps the admin token in an httpOnly cookie and forwards each browser request to /api/v1/admin/... from its own server, so the browser never talks to the API directly and no CORS setup is needed.
Backend → PostgreSQLAll data lives here. Only the backend connects.
Backend → SMTP, R2One-time codes for sign-up and password reset are sent by email through your SMTP account. Images uploaded in the admin panel (region flags, push images) go to Cloudflare R2.
Backend → Firebase Cloud MessagingPush notifications written in the admin panel are sent by the backend.
App ↔ RevenueCat → BackendThe app buys a subscription through Google Play or the App Store with the RevenueCat SDK. RevenueCat then calls the backend's webhook, and the backend grants or removes Premium.
App ↔ AdMob → BackendA free user watches a rewarded ad. AdMob calls the backend's server-side verification URL, and only then does the backend add VPN time.

4. Firebase Setup

Firebase provides Google sign-in, push notifications, Analytics and Crashlytics. It is optional: without it the app runs with email sign-in, and the Google button, push, Analytics and Crashlytics are switched off automatically.

Use your own Firebase project. The package ships placeholder files with values such as YOUR_FIREBASE_.... They let the project compile, but Firebase features stay off until you replace them:
  • sable-vpn/lib/firebase_options.dart
  • sable-vpn/android/app/google-services.json
  • sable-vpn/firebase.json
There is no iOS Firebase file in the package, so on iOS Firebase only works after step 2 below. No Firebase project of ours is included.

Step 1: Create a Firebase project

  • Open the Firebase console and click Create a project. Enter a name and accept the terms.
  • Choose whether to enable Gemini, and enable Google Analytics if you want the in-app Analytics, then click Create project.

Step 2: Connect the app (FlutterFire CLI)

Change the package name and bundle ID first (section 3). The FlutterFire CLI then registers your Android and iOS apps and writes the config files:

npm install -g firebase-tools
firebase login
dart pub global activate flutterfire_cli
cd sable-vpn
flutterfire configure --project=<your-firebase-project-id>

Select android and ios and confirm your IDs. The command updates lib/firebase_options.dart, android/app/google-services.json, ios/Runner/GoogleService-Info.plist and firebase.json. The Android build turns on the Firebase and Crashlytics Gradle plugins by itself once google-services.json no longer contains placeholders.

Step 3: Enable sign-in methods

  • Open Build > Authentication > Sign-in method and enable Google. (Email sign-in does not use Firebase; the Sable backend handles it.)

Step 4: Service account for the backend

The backend checks Google sign-ins and sends push notifications with a Firebase service account: Project settings > Service accounts > Generate new private key. Paste the JSON in the admin panel (Settings > Integrations) or put it in the backend .env (section 13, step 7).

5. Social Sign-In and Push Notifications

Google

  • Enable Google in Firebase Authentication (section 4, step 3).
  • Android: add your SHA-1 and SHA-256 fingerprints in Project settings > Your apps > Android: the debug key, your upload key and, after publishing, the App signing key from Play Console.   • iOS: in ios/Runner/Info.plist, replace YOUR_IOS_CLIENT_ID in two places with the iOS client ID from GoogleService-Info.plist: the GIDClientID value (<id>.apps.googleusercontent.com) and the URL scheme com.googleusercontent.apps.<id> (the REVERSED_CLIENT_ID).

Apple

Sign in with Apple is not included in this version. The backend accepts only Google tokens, so the Apple button is hidden in the app. The code is kept but commented out in lib/data/auth/firebase_social_identity.dart for a future update. Email and Google sign-in are not affected.

Apple's App Review Guideline 4.8 asks apps that offer a third-party sign-in such as Google to also offer an equivalent private sign-in option. Email and password sign-in is available in Sable; check the current guideline before you submit and be ready to explain your sign-in options to App Review.

Push notifications

  • Android: works once google-services.json is in place and the backend has the service account. Notifications use the channel high_priority_channel.
  • iOS: in Xcode select the Runner target > Signing & Capabilities > + Capability > Push Notifications (Remote notifications background mode is already set in Info.plist). Create an APNs key in your Apple Developer account and upload it in Firebase: Project settings > Cloud Messaging > Apple app configuration.
  • The app registers each device's push token with the backend, and the admin panel sends to those tokens. There is no topic name to keep in sync.

7. App Icon, Splash, Colours and Font

App icon and splash

All launcher icons, the notification icon and the splash image are generated from one picture, assets/brand/sable_silhouette.png:

  • Replace assets/brand/sable_silhouette.png with your own logo (a PNG with a transparent background, the same pixel size as the original).

  • The icon and splash background colour is #16408C, set in android/app/src/main/res/values/colors.xml (splash_primary) and res/values/ic_launcher_background.xml. Change both to your brand colour before you generate.
  • The animated start screen in the app is lib/design/brand/sable_boot_artwork.dart; the logo mark is lib/design/brand/sable_mark.dart.

Brand colours

All app colours are in lib/design/tokens/sable_colors.dart, with a light set (SableColors.light) and a dark set (SableColors.dark). Flutter writes colours as 0xAARRGGBB: FF (fully opaque) followed by the normal hex code.

// lib/design/tokens/sable_colors.dart
// SableColors.light
primary: Color(0xFF16408C),        // brand blue #16408C
connected: Color(0xFF1D50B5),      // the connect dial when connected

// SableColors.dark
primary: Color(0xFF5B8DEF),        // brand blue for dark mode #5B8DEF
connected: Color(0xFF6FA0FF),

Example: to use orange #FF6B00, change the light primary to Color(0xFFFF6B00) and pick a lighter orange for dark mode, then stop the app and run it again (hot reload does not update const colours). Screens read colours only from this file; a test (test/design/tokens_test.dart) fails if a screen uses a hard-coded colour.

Font

The app uses Inter Tight through the google_fonts package, which downloads the font the first time the app opens. On networks that block Google Fonts the app falls back to the system font. To ship the font inside the app instead, add the font files under flutter: fonts: in pubspec.yaml and change face in lib/design/tokens/sable_typography.dart to use fontFamily.

8. Connect the App to Your Backend

Set your backend address in lib/core/config/auth_api_config.dart:

// lib/core/config/auth_api_config.dart
static const String origin = String.fromEnvironment(
  'AUTH_API_BASE_URL',
  defaultValue: 'https://api.your-domain.com',   // ← your backend, origin only

Enter the origin only (no /api/v1); the app adds /api/v1/... itself. You can also leave the file alone and pass the address when you build: --dart-define=AUTH_API_BASE_URL=https://api.your-domain.com.

HTTPS in release builds. Release builds only allow HTTPS. Plain HTTP is allowed only in Android debug builds (for testing against http://<your-computer-ip>:3001 on the same Wi-Fi). Put the backend behind HTTPS before you test a release build or an iPhone build.

9. Languages

The app ships with English, Bangla, Arabic, Russian and Ukrainian. Users pick a language on Account > Language; the app starts in English until they do.

What a language entry looks like

All texts live in one Dart file, lib/core/i18n/app_strings.dart. The keys are in lib/core/i18n/string_keys.dart. Each key has one line per language:

// lib/core/i18n/app_strings.dart
StringKeys.profile: {
  "en": "Profile",
  "bn": "প্রোফাইল",
  "ar": "ملف شخصي",
  "ru": "Профиль",
  "uk": "Профіль",
},

To change a text, edit its line. A missing translation falls back to English for that key only.

Add a language

Example: adding French (fr).

  1. In app_strings.dart, add 'fr' to AppStrings.supported, and add a case for 'fr' in _getLocal().
  2. Add "fr": "..." to every entry in localStrings in the same file: 
    StringKeys.profile: {
  "en": "Profile",
  ...
  "uk": "Профіль",
  "fr": "Profil",
},
  3. In lib/features/preferences/bloc/locale_cubit.dart, add an entry for French to languages (the code and the name shown in the picker, Français).
  4. In lib/app/app.dart, add Locale('fr') to supportedLocales.

Remove a language

Do the same steps in reverse: remove the code from AppStrings.supported, _getLocal(), LocaleCubit.languages and supportedLocales. The extra lines in localStrings can stay; they are simply not used.

Default language

English is the default in three places: languageCode = 'en' in app_strings.dart, and the starting value and fallback in locale_cubit.dart. Change all three to start in another language.

Right-to-left layout. Arabic texts are translated, but in this version the screen layout stays left-to-right. To mirror the layout for Arabic, add the flutter_localizations package and set localizationsDelegates (with GlobalWidgetsLocalizations.delegate) on the MaterialApp in lib/app/app.dart. A few labels, such as the bottom tab names in lib/app/router/shell/app_shell_page.dart, are written in English directly in the code.

As a fallback you can also put your Android rewarded unit in liveAndroidRewardedUnitId in lib/core/config/admob_config.dart.

Step 3: Server-side verification (required for rewards)

The backend adds time only after Google confirms the ad was watched. In AdMob, open your Rewarded ad unit > Server-side verification and set the callback URL to:

https://api.your-domain.com/api/v1/webhooks/admob-ssv

The app passes the user's ID and a one-time code with each ad; the backend checks Google's signature and the code before adding time. Optionally restrict which ad units may grant rewards with ADMOB_REWARDED_AD_UNIT_IDS in the backend .env or the ad unit list on the Rewarded ads page.

Reward rules

On Plans & billing > Rewarded ads you set: rewards on or off, the reward ladder (minutes per ad, by default 30, 50, 60, 90 and 120), rewards per day per user and per device (5), the wait between ads, the most time a user can bank (4 hours), banner on or off, interstitial on or off and how often (every 3 connects). The same page shows a log of every reward and why any was refused.

11. Premium Subscriptions (RevenueCat)

Premium is sold as Google Play and App Store subscriptions through RevenueCat. The app buys through the RevenueCat SDK; RevenueCat tells your backend about every purchase, renewal, cancellation and refund through a webhook, and the backend grants or removes Premium. The app never grants Premium by itself.

Step 1: Create the products in the stores

  • Google Play Console > your app > Monetize > Subscriptions: create a subscription with base plans, for example a monthly and a yearly one. (Upload a build with billing to a testing track first; Play Console requires it.)
  • App Store Connect > your app > Subscriptions: create a subscription group with a monthly and a yearly product.

Step 2: Set up RevenueCat

  • Create a RevenueCat project, add your Android and iOS apps and connect them to the stores (Google service-account credentials and the App Store in-app purchase key, as RevenueCat's setup guide describes).
  • Import your products and create a current offering with a monthly and a yearly package.
  • Copy the public SDK keys (they start with goog_ and appl_).

Step 3: Connect RevenueCat to Sable

  • In the admin panel open Settings > Integrations and enter the RevenueCat Android key and iOS key. The app reads them from the backend at start.
  • Generate a webhook secret: openssl rand -hex 32. Enter it as RevenueCat webhook secret on the same page (or REVENUECAT_WEBHOOK_AUTH in the backend .env).
  • In RevenueCat open Integrations > Webhooks, add https://api.your-domain.com/api/v1/webhooks/revenuecat and set the Authorization header to exactly the same secret.

Step 4: Match the products to your plans

In the admin panel open Plans & billing > Store products. For each store product, enter the exact product ID from the store and choose the plan it grants. The first start created example products (com.sablevpn.app.premium.monthly, com.sablevpn.app.premium.yearly, and sable_primium_subscription:monthly-premium-base-pack / ...:yearly-premium-base-pack for Google Play): change them to your own IDs. For Google Play use the subscriptionId:basePlanId form.

Then check the plans on Plans & billing > Plans: name, price and currency shown on the paywall, devices, limits and features. The example plans use BDT prices; change them to your own currency and prices.

How it works

  • The paywall lists the active plans from the backend and buys the matching store product. Users must be signed in to buy, and the purchase is linked to their Sable account.
  • After a purchase the app waits for the backend to confirm Premium (usually a few seconds). Restore purchases on the paywall handles reinstalls and new phones.
  • Failed webhook events are retried every 10 minutes and can be replayed on Plans & billing > Payment events.
  • Keep RevenueCat sandbox switched on in Settings: App Review tests your app with sandbox purchases.
  • You can also give Premium without a purchase: on a user's page in the admin panel use Grant premium, or create promo codes.
Not included: Stripe, PayPal and other web checkouts. bKash and Nagad appear as switched-off rows in the database but have no checkout; leave them off.

Account deletion

Apple and Google require that users can delete their account from inside the app. Sable does this in two steps, the common pattern for apps with paid plans: the account is blocked at once, then deleted automatically after a grace period, so a request made by mistake can still be cancelled.

  1. The user asks. In the app: Account → Delete account. An email account confirms with its password; a Google account does not need one. The screen says when the account will be deleted and that an app store subscription is not cancelled with it.
  2. Blocked at once. Every device is signed out, VPN tunnels close and push notifications stop. Signing in again shows “This account is scheduled for deletion”. In the admin panel the user shows as Deletion requested, with the reason and the deletion date.

15. VPN Servers and the Node Agent

Your users' traffic flows through VPN servers that you rent and control. Each one runs WireGuard, optionally Xray for V2Ray (VMess over TLS), and the small Sable node agent, which keeps the server in sync with the backend. You add servers from the admin panel; one copy-and-paste command sets each one up.

What a VPN server needs

Requirement
Operating systemUbuntu 22.04 or 24.04, or Debian 12, with systemd. The installer refuses other systems
CPU and memoryx86_64 or ARM64, at least 1 GB RAM
NetworkA public IPv4 address and outbound HTTPS to your API. Choose a plan with enough monthly bandwidth: every byte your users send and receive passes through this server
AccessRoot (or sudo) over SSH
FirewallOpen UDP 51820 for WireGuard. For V2Ray also open TCP 443 and TCP 80 (80 is used to get the TLS certificate). Open them in your provider's cloud firewall too; the installer opens ufw itself when ufw is active
Domain (V2Ray only)A hostname such as sg1.your-domain.com whose DNS A record points to the server's public IP, so a Let's Encrypt certificate can be issued
Use a separate, clean server for VPN traffic, not the one that runs the backend. Do not run nginx or another web server on it: the V2Ray setup needs ports 80 and 443 for itself.

Step 1: Add a region

In the admin panel open Regions and add the location: code (for example sg-sin-01), name, country code, city, map position, a flag image, the access level (Free, Ads or Premium) and the sort order. The first start of the backend created an example region, Jakarta, with a placeholder server; edit or delete them.

Step 2: Add the server (the wizard)

Open Servers > Add server. The wizard has five steps:

  1. Details — region, display name, hostname, public IPv4, provider, access level, maximum connections and bandwidth. Turn WireGuard on (UDP port 51820) and, if you want, V2Ray (VMess) with its TCP port and TLS.
  2. IP pool — the private addresses given to WireGuard clients. The default 10.8.0.0/24 (gateway 10.8.0.1, DNS 1.1.1.1, 1.0.0.1) serves about 250 users at once; use 10.8.0.0/22 for more. This step is skipped when WireGuard is off.
  3. Install — the panel creates the server in maintenance mode and shows a one-time install command. The agent token inside it is shown only once; copy the command before you continue.
  4. Verify — run the command on the server (step 3). The panel checks every 3 seconds until the agent has reached the API, registered its WireGuard key and sent its first heartbeat.
  5. Go live — the panel lists anything still missing. Click Activate server to make it available in the app.

Step 3: Run the install command on the server

SSH into the new server and paste the command from the panel. It looks like this:

curl -fsSL 'https://api.your-domain.com/api/v1/node-agent/install-agent.sh' \
  | sudo bash -s -- --api 'https://api.your-domain.com/api/v1' \
      --server-id '<server id>' --token '<one-time token>'

The script, in order:

  • checks it runs as root on a supported system, and installs curl, jq and a few basic tools;
  • asks the API for this server's settings (a 401 here means a wrong server ID or token);
  • installs Node.js 22 from nodejs.org (checksum verified) if Node.js 20 or newer is missing;
  • WireGuard: installs it, creates /etc/wireguard/wg0.conf with a new key and NAT, starts wg-quick@wg0 and registers the public key with the API;
  • V2Ray (if enabled): installs Xray-core (checksum verified) as the xray service, gets a Let's Encrypt certificate for the hostname, and blocks traffic to private addresses;
  • Agent: installs it in /opt/vpn-node-agent, writes its settings to /opt/vpn-node-agent/.env (readable by root only) and starts the vpn-node-agent systemd service.

It ends with "Agent is running". Back in the panel the Verify step turns green.

Options: --skip-wireguard (V2Ray only), --iface NAME (WireGuard interface name, default wg0), and --insecure-http (allows an http:// API address; only for testing on a private network).

What the agent does

  • Every 30 seconds it sends a heartbeat: CPU, memory, load, connected peers and bandwidth. These numbers appear on the Dashboard and the server page.
  • Every 5 seconds it asks the API for peers to add or remove, and applies them to WireGuard and Xray. So a user can connect a few seconds after tapping Connect.
  • It signs every request with its own agent token. The backend stores only a hash of the token.
  • It opens no ports. If a server stops sending heartbeats for 120 seconds, the backend marks it unreachable and stops sending users to it.

systemctl status xray                                # if V2Ray is enabled

16. API Reference

All endpoints live under https://api.your-domain.com/api/v1. The full, always-current reference with every request body is the Swagger UI at /api/docs (when SWAGGER_ENABLED is on). This section covers the conventions and the most important calls. The JSON below was captured from a real server or built from the request classes in the code.

Conventions

  • Requests and responses are JSON. Uploads use multipart/form-data with a field named file.
  • Unknown fields in a request body are rejected with 400 ("property … should not exist").
  • IDs are UUIDs. Times are ISO 8601 in UTC.
  • Rate limit: 100 requests per 60 seconds per IP by default (THROTTLE_TTL_MS, THROTTLE_LIMIT), with tighter limits on sign-in, codes, connect and promo codes. Admin routes allow 60 per minute. Over the limit you get 429.
  • Device headers. auth/signup, auth/login and auth/social require X-Device-Id (a stable ID per install, up to 128 characters) and X-Platform (android, ios, windows, macos, linux or tv). Optional: X-Device-Model, X-OS-Version, X-App-Version, X-App-Build, X-Locale. Other routes take the device from the token.

The response envelope

// success
{ "success": true, "data": { ... } }

// error (real response)
{ "success": false,
  "error": { "code": "UNAUTHORIZED", "message": "Invalid credentials" },
  "path": "/api/v1/auth/login", "timestamp": "2026-10-25T10:19:58.275Z" }

// validation error: message is a list (real response)
{ "success": false,
  "error": { "code": "BAD_REQUEST", "message": ["user_name must be an email", "password must be a string"] },
  "path": "/api/v1/auth/login", "timestamp": "2026-10-25T10:19:53.928Z" }

The health check (GET /health) and the agent files (GET /node-agent/:name) are not wrapped. Some errors carry extra fields; for example DEVICE_LIMIT_EXCEEDED includes limit, devices and a device_manage_token the app uses to sign another device out.

Pagination (admin lists): ?page=1&limit=20 (maximum 100). The response data is { "items": [...], "page": 1, "limit": 20, "total": 57 }.

17. Database Schema

PostgreSQL 14 or newer, managed with TypeORM. The tables are created by the migrations in sable-backend/src/database/migrations/, which run when the server starts (DB_RUN_MIGRATIONS=true). sable-backend/database/schema.sql holds the same schema and default data if you prefer to create the database by hand.

Conventions

  • IDs are UUIDs; times are timestamptz.
  • Email addresses use citext, so they are compared without regard to case.
  • Lists and settings are stored as jsonb (plan features, protocol settings, app settings, audit before/after).
  • vpn_sessions is partitioned by month on started_at. The backend creates the next two months' partitions at start and every night at 02:00.
  • Extensions: citext, pg_trgm, pgcrypto, uuid-ossp.

General questions

QuestionAnswer
Are VPN servers included?No. You rent your own servers from any provider and add them in the admin panel; one command sets each one up (section 15).
How many users can one server handle?It depends mostly on its network speed and bandwidth allowance. By default each server accepts 250 connections and each IP pool gives out about 250 addresses; raise both for bigger servers.
Which protocols are supported?WireGuard and V2Ray (VMess over TLS), plus Auto. V2Ray is offered only on plans without a speed limit, because speed limits are applied to WireGuard.
Can I sell Premium on both Android and iOS?Yes, through Google Play and the App Store via RevenueCat (section 11).
Can I add another payment gateway?Yes, as custom development. Plans, gateways and products are separate tables, so a new gateway needs a checkout and a webhook that grants the plan.
Does the app work without Firebase?Yes. Email sign-in, connecting, ads and Premium work; Google sign-in, push, Analytics and Crashlytics are off.
Can I host the backend and admin panel on one server?Yes. Use two nginx server blocks (for example api. and admin. subdomains). Keep VPN servers separate.
What is lib/main.demo.dart?A developer preview entry point (flutter run -t lib/main.demo.dart) that skips Firebase and fakes the signed-in session. It still needs a running backend for servers and plans. Use the normal lib/main.dart for real builds.
Are any files minified or obfuscated?No. All three projects ship as readable source code. The only pre-built binaries are the VPN core libraries in packages/flutter_vpncore/android/libs/ and ios/Frameworks/.

21. Upgrading to a New Version

When a new version of Sable is released, download it from your CodeCanyon Downloads page and read its changelog first. Your users, servers, plans, subscriptions and settings live in your PostgreSQL database, not in the code, so updating the code does not delete them.

Before you start

  • Back up the database (see section 17, Backups): 
    pg_dump -Fc -d sable -f sable-before-upgrade.dump
  • Keep your own changes in Git, or note which files you edited, so you can carry them over.
  • Never overwrite these files with the ones from the new package; they hold your settings:
    ProjectKeep your copy of
    Backend.env, and prod.config.js if you changed the PM2 name or memory limit
    Admin panel.env, and prod.config.js or the port in package.json if you changed them
    Flutter applib/firebase_options.dart, android/app/google-services.json, ios/Runner/GoogleService-Info.plist, android/key.properties and your keystore, secrets.json, lib/core/config/auth_api_config.dart, lib/core/config/admob_config.dart, ios/Flutter/*.xcconfig, ios/Runner/Info.plist, your bundle IDs and App Group (section 3), your icons and assets/brand/, and lib/design/tokens/sable_colors.dart
  • Compare the new .env.example files with your .env files and add any new variables.

Carrying your own code changes forward

If you edited source files (not only settings), do not copy the new version straight over them. The safest way is Git:

# one time, before your first customisation
cd sable-backend            # or sable-admin, or sable-vpn
git init && git add -A && git commit -m "Sable 1.0.0 original"
# ...make your changes and commit them as usual...

# when a new version arrives
git checkout -b upgrade
# copy the new package files over the folder (keep the files listed above)
git add -A && git commit -m "Sable 1.x.x original"
git checkout main && git merge upgrade      # Git combines both; fix any conflicts it lists

Without Git, compare your old folder and the new one with a diff tool (VS Code: right-click two files > Compare Selected) and re-apply your edits to the new files.

1. Backend

cd sable-backend
# copy the new files over your old folder, keeping your .env
npm ci
npm run build
pm2 reload sable-api
  • Database changes are applied automatically. With DB_RUN_MIGRATIONS=true the server runs every new migration when it starts. Each migration runs once and is recorded in the migrations table.
  • Migrations keep your existing rows. If a release ever needs to change existing data, its changelog says so.
  • Check what ran: npm run migration:show. If something goes wrong, npm run migration:revert undoes the last migration, or restore the backup with pg_restore -d sable --clean sable-before-upgrade.dump and go back to the old code.
  • Never edit an existing migration file; add a new one instead (npm run migration:generate).

2. VPN servers

If the changelog mentions the node agent, run the update command on each VPN server (section 15). It keeps the server's settings and token.

3. Admin panel

cd sable-admin
# copy the new files over your old folder, keeping .env
npm ci
npm run build
pm2 restart sable-admin

The admin panel stores nothing itself; all data comes from the backend. Upgrade the backend first.

4. Flutter app

  • Copy the new lib/, packages/, assets/ and pubspec.yaml over your project, then restore the files you customised (list above). If you use Git, commit first and review the diff.
  • Run: 
    flutter clean
flutter pub get
cd ios && pod install && cd ..
flutter run
  • Raise version: in pubspec.yaml (for example 1.0.1+2) and publish the update as in section 12.
  • Old app versions keep working with the new backend unless the changelog says otherwise. To make everyone update, raise the minimum version on the admin panel's App config > Versions page.
